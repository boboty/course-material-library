# Task 005 — 完整候选集分页截断修复

## 背景

后端分页接口将 `page_size` 上限固定为 100，这是正常且不改变的设计。

但前端有若干“需要完整候选集”的选择场景只请求了第一页 100 条：

- 场次创建页的客户、启用课程、人群类型；
- 客户创建 / 编辑页的行业；
- 词表维护页的行业与人群类型。

当实体数量超过 100 后，后续实体在页面上根本不存在，用户无法选择，也无法在词表维护页看到完整列表。

已在 Task 4 独立验收中记录为 P2 后续缺陷：人群词表超过 100 条时场次页加载不全；复用积累较多数据的默认 E2E 库（`benyan_e2e` 已有 112 条人群类型）会触发相关超时。

本 Task 是独立小修复，不新增任何业务能力。

## 基线

- Task 4 accepted baseline：`b08aa3fbbc8b0e7196a9827b50f9d6df491a3e9d`
- Migration head：`0003_usages`（单一 head）

施工前必须确认仓库仍基于该已验收能力继续，不破坏 Task 1–4 已冻结语义。

## 目标

**需要完整候选集的前端场景，无论实体数量多少，都能加载到全部数据；后端分页契约保持不变。**

## 本 Task 范围

### 1. 前端 API 层提供可复用的分页取全能力

在 `web/src/api/client.ts` 增加统一的分页取全 helper，按后端允许的最大 `page_size`（100）逐页请求，直到取满 `total`。

- 页面层不得各自实现分页循环；
- 需要完整候选集的场景统一通过该 helper 取全；
- 保持 `Page<T>` 与既有 `request` / `pageQuery` 契约不变。

### 2. 场次创建页加载全部候选

`/sessions/new` 必须能加载全部：

- 客户；
- 启用状态的课程；
- 人群类型。

### 3. 客户创建 / 编辑页加载全部行业

`/customers/new` 与 `/customers/:id/edit` 的行业下拉必须包含全部行业。

### 4. 词表维护页完整显示

`/vocabularies` 的行业与人群类型必须完整显示全部条目，数量显示与后端 `total` 一致。

### 5. 后端分页契约保持不变

- 不修改任何后端分页接口；
- 不提高 `page_size` 上限；
- 不新增分页聚合接口。

### 6. 验证

- 前端单元测试覆盖分页取全 helper 与相关 API 包装函数；
- E2E 增加 101+ 实体场景的真实流程覆盖。

- 素材搜索等按关键词分页的既有交互改造；
- 新基础设施（缓存、状态管理库、请求库）。

## 验收场景

1. 人群类型超过 100 条时，第 101 条及之后的条目仍能在 `/sessions/new` 选中，并能成功创建场次；
2. 客户超过 100 条时，第一页之后的客户可选；
3. 启用课程超过 100 条时，第一页之后的课程可选；
4. 行业超过 100 条时，客户表单可选第一页之后的行业；
5. 词表维护页显示的行数与数量与后端 `total` 一致；
6. 原有分页 API 行为不变（`page` / `page_size` / `total` 语义与上限校验不变）；
7. Task 1 / Task 2 / Task 3 / Task 4 全部回归通过；
8. 累积超过 100 条人群类型的默认 E2E 库（`benyan_e2e`）不再因此超时。
